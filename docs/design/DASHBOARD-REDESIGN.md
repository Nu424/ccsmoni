# ダッシュボード再設計のブリーフ

> 経緯の記録。ここで比べた3つのプロトタイプ（`prototypes/`）は、公開前に削除した。コミット `319346a` に残っている。採用した設計は [UI-V2.md](UI-V2.md)。

目標: **1画面（PC 1440×900 前後）に情報がみっちり詰まり、それでいて一目でわかる、スタイリッシュなダッシュボード**。
主役は、各アカウントの使用率の**推移**（PLAN U1）。そのうえで、今の値・リセットまでの時間・ヒント・ログイン切れの対処も、同じ画面で完結させる。

## 現状の課題（v1 の画面から洗い出したもの）

### レイアウト・密度
1. **カードの高さがばらばら**。ヒントの行の有無、ログイン切れカードの大きなログイン欄、未開始の行などで高さが変わり、グリッドがガタガタになる。6アカウントだと2段になり、右下に「無効なアカウント」の枠が浮く。
2. **1画面に収まらない**。カード（2段）＋グラフ＋週ピーク表で縦にスクロールが必要。上下の余白とカード内の余白が大きく、情報の密度が低い。
3. **同じ情報が重複している**。アカウントの識別がカードと凡例の2か所にあり、凡例は操作のためだけに場所を取っている。
4. **ログイン切れの欄が大きすぎる**。めったに使わない操作が、常にカードの 1/2 を占める。

### グラフ
5. **点（マーカー）がない**。10分ごとの観測が階段状の線になるだけで、どこが実測なのか、取得が抜けた所がどこなのかがわかりにくい。
6. **週間と 5h が同時に見られない**（切り替え式）。5h の消費が週間をどう押し上げたか、という関係が見えない。
7. **線の終端（＝今）に値のラベルがない**。凡例の色と線を見比べないと、どの線がどのアカウントかわからない。
8. 記録が短いうちは、グラフの大部分が空白になる（v1 で左端を詰めたが、それでも密度が低い）。

### 色・状態
9. アカウントの色が CVD（色覚多様性）の検証を通っていない。状態の色（危険＝赤）と、アカウントの色（赤系）がぶつかることがある。
10. 使用率のバーが小さく（幅 80px 程度）、ペースの目盛りも見づらい。

### 週ピーク表
11. 記録が短いと、ほとんど空。長くなると横に間延びする。画面の中での位置づけ（主役のグラフとの関係）が弱い。

## 3つの方向性（それぞれ独立したプロトタイプにする）

### A. マトリクス（Cockpit）
アカウント＝行の、高密度の表。行の高さは固定なので、全行の高さがそろう。
- 列の例: 色・名前・プラン｜5h のメーター（目盛り付き）＋残り時間｜週間のメーター＋残り時間｜**行内のスパークライン**（7日の週間の線と、5h の面。点付き）｜直近の週ピーク（小さなセル4〜6個）｜ヒント・状態（1行のアイコン＋短文。ログイン切れなら小さな［ログイン］ボタン）
- 行の下（または上）に、大きな重ね合わせのグラフ。行にホバーすると、そのアカウントの線が強調される。
- 行が凡例を兼ねる（行の先頭のチェックで表示／非表示）。

### B. タイル（Small multiples）
全アカウントを、**同じ大きさのタイル**で 3×2 などのグリッドに並べ、画面を埋める。
- 各タイル: 名前・状態の帯｜大きな数字（週間 % と 5h %）｜そのアカウント専用のミニチャート（週間の線＋5h の面、点付き、リセット線、x 軸は全タイルで共通）｜下端に1行のヒント。
- 上部に全体の帯（最終更新、次の更新、要注意の件数のサマリー）。比較用の重ね合わせグラフは、切り替えか小さなパネルにする。
- ログイン切れのタイルは、グラフの代わりに「最後にわかった値」と［ログイン］を出す。タイルの大きさは変えない。

### C. レール＋分析（Timeline）
左に細いレール（アカウントの一覧。今の値を小さなリングかバーで表示）。右に大きな分析エリア。
- 分析エリアは、上下に**x 軸を共有する2段のグラフ**: 上に週間（重ね合わせ・点付き・線の終端に直接ラベル）、下に 5h（重ね合わせ、または積み上げない面）。カーソルは同期する。
- 右下か下段に、週ピークのヒートマップをコンパクトに。
- レールの項目が凡例を兼ねる（押すと表示／非表示、ダブルクリックでそれだけ表示）。ヒントやログイン切れは、レールの項目内にアイコンで示し、ホバーで詳細を出す。

## 共通の条件
- データは `prototypes/demo-data.js`（`window.CCSMONI_DEMO`）を使う。中身は ccsmoni の API 応答（docs/API.md の形）のスナップショット。キーは state, history_24h, history_7d, history_30d, windows_weekly, windows_session。
- **6アカウントでの見え方も必ず確認する**。デモは4アカウントなので、URL に `?n=6` を付けたら、既存のアカウントを複製・改変して6件にする（id・色・値を少し変える）。実際のユーザーは6〜7アカウント。
- ライトとダークの両方。スマホ幅（390px）では縦に積んで崩れないこと（1画面に収める目標は PC だけでよい）。
- 色はアカウントの識別（categorical）と状態（status）を分ける。categorical のパレットは dataviz スキルの validator で検証する。
- グラフには点を付ける。ただし「すべての点にラベル」は付けない。直近の値（終端）だけラベルにする。
- 実装: 1ファイルの HTML（`prototypes/<名前>.html`）＋必要なら同名の .js/.css。外部 CDN は使わない。グラフは uPlot（`../src/ccsmoni/static/vendor/` にある）でも、自前の SVG／canvas でもよい。

## 比較（2026-10-27、3案の完成後）

見方: `uv run python -m http.server 8660` をリポジトリのルートで実行し、http://127.0.0.1:8660/prototypes/ を開く。

| 観点 | A マトリクス | B タイル | C レール＋分析 |
|---|---|---|---|
| アカウント同士の比較 | ◎ 行がそろっていて、数字・メーター・週ピークを縦に読み比べられる | △ タイルをまたいで数字を読み比べる必要がある（「重ねる」表示で補う） | ○ レールで読み比べられるが、項目が縦に長い |
| 推移（主役） | ◎ 週間の重ね合わせが大きく、5h は**アカウントごとのレーン**で縞模様にならない | ○ アカウントごとの推移は一番見やすい。全体の比較は弱い | ○ 週間は見やすい。5h の重ね合わせは 7日・30日で縞模様になる |
| 週間と 5h の関係 | ◎ x 軸を共有するレーンで、縦にそろう | ◎ 同じグラフに重ねる | ○ 2段のグラフ（5h が読みにくい） |
| 情報の密度 | ◎ | ○ | ◎ |
| 落ち着き・初見のわかりやすさ | ○ 記号が多く、説明が要る | ◎ いちばん直感的 | ○ |
| 件数への強さ（7件以上） | ○ 表とレーンが伸びて、グラフが縮む | △ タイルが小さくなる | ○ レールがスクロールする |
| スマホ | △ 表がカードになり、行の利点が消える | ◎ タイルを縦に積むだけ | ○ |

共通の改善（どの案を選んでも本実装に入れる）:
- 検証済みの7色パレット（赤はアカウントの色に使わない。状態の色とは別系列）。サーバーは hex ではなく、**色の番号（color_slot）**を返し、ライトとダークで別の色の段を使う。
- 観測点を描く（期間に応じて間引く）。終端に直接ラベル。状態はアイコン＋文言。
- ログイン切れは1行に収め、詳細はポップオーバーに出す。
